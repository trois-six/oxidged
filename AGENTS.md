# oxidged Development Guide

## Project

oxidged is a Rust library that reads any GEDCOM file leniently, without losing
data, and writes strictly conformant GEDCOM 5.5.1, 7.0 and 7.1. The repository
is a workspace of the library (the root) and its command-line tool
(`oxidged-cli`, in `cli/`); the fuzz targets (`fuzz/`) and the tools
(`tools/perf`, `tools/differential`, `tools/spec-tables`) are packages of their
own.

## Principles

- Quality and conformance first: the writer emits strictly conformant GEDCOM
  5.5.1, 7.0 and 7.1, writes are idempotent, and the reader is lenient (it
  keeps all data and warns about nothing).
- Every feature the documentation describes keeps working, and performance
  does not regress (`tools/perf check`, instruction counts).
- Compatibility with the API of other crates, ged_io included, is not a goal.

## Documentation

- `docs/` is a conformant
  [OKF v0.2](https://github.com/GoogleCloudPlatform/open-knowledge-format/blob/main/SPEC.md)
  bundle. Every document but `index.md` starts with a YAML frontmatter block
  with `type`, `title` (its H1), `description` (one sentence), `tags` (a list
  starting with `oxidged`) and `generated: { by: human:maintainer, at: <ISO
  8601 UTC> }`, `at` updated on every substantive edit. `index.md` carries only
  `okf_version: "0.2"`, then `#` sections of `* [Title](file.md) - description`
  entries whose descriptions match the documents' frontmatter word for word.
  `tests/docs.rs` checks all of it.
- The documentation describes what the crate does now, exhaustively. It is
  not a history: no changelog, no "since version X", no migration guide. What
  changed is said by the commit messages.
- Planned work lives in `docs/roadmap.md` only.
- The README keeps the main features, a few command-line examples, building,
  documentation links, contributing, origin and licence; everything else is in
  `docs/`.
- Rust examples in `docs/` are compiled and run as documentation tests
  (`src/lib.rs`).

## Language and data

- English only in code, comments, documentation and commit messages.
- Test data, examples and fixtures are fictitious.

## Git

- Conventional Commits, an imperative subject and a detailed body: what
  changed, why, the design decisions and the verification performed.
- Commits are authored by the maintainer. Commit messages, pull requests and
  every file carry no AI attribution: no `Co-Authored-By` trailer naming a
  tool or model, no "generated by" line, no session link, no tool name.
- Work is committed directly on `main`; no pull request unless asked.

## Verification

A change limited to documentation (`docs/`, the READMEs, `AGENTS.md`) or to
GitHub Actions workflows needs only focused validation: `cargo test --test
docs` for `docs/` and the READMEs (and `cargo test --doc --all-features -p
oxidged` when a Rust example changes), a YAML parse of an edited workflow.

Before committing code: `cargo fmt --all --check` (and in `fuzz/` and each
tool), `cargo clippy --workspace --all-targets -- -D warnings` with all
features, and on the library (`-p oxidged`, which the CLI's features would
otherwise unify) with none and each feature alone, `cargo test --workspace
--all-features` and `cargo test -p oxidged --no-default-features`, `RUSTDOCFLAGS="-D warnings" cargo doc --workspace
--no-deps --all-features`, and the MSRV (`cargo +1.88 test --workspace
--all-features`).
